# 100 млн голосов за минуту: расчёт мощности

Это **план оценки и испытаний**, а не заявление, что локальный сервис выдержал национальный эфир. Все числа ниже, кроме арифметики из условия, являются явными допущениями. Измеренные результаты следует читать отдельно в отчёте нагрузочного прогона.

## Поток голосов и HTTP-запросов

```text
N = 100 000 000 участников
T = 60 секунд
Ravg = N / T = 1 666 666,7 уникальных голосов/с
```

100 млн — число участников, а не число записей во всех таблицах, HTTP-запросов или выбранных вариантов. При вопросе с выбором нескольких вариантов один ballot может увеличить несколько счётчиков.

| Сценарий | Требуемый поток |
| --- | ---: |
| Равномерное голосование всю минуту | 1,67 млн новых ballots/с |
| Треугольный всплеск длительностью 60с с тем же числом участников | Пик 3,33 млн ballots/с |
| Проектный кратковременный пик ×5 среднего, **допущение** | 8,33 млн ballots/с |
| Реализованный first visit: GET metadata + POST session + POST vote | 300 млн origin requests, среднее 5,00 млн/с |
| GET metadata обслужен CDN; session + vote остаются на origin | 200 млн origin requests, среднее 3,33 млн/с |
| Дополнительно 10% повторов POST, **допущение**, без CDN metadata | 310 млн origin requests, среднее 5,17 млн/с |
| Те же повторы с cached metadata | 210 млн origin requests, среднее 3,50 млн/с |

Пик ×5 нельзя поддерживать все 60с и одновременно называть общую аудиторию 100 млн. Это условие кратковременного headroom; длительность и форма пика должны прийти из данных телевизионного трафика. Ролик сразу показывает QR, поэтому безопасно ожидать коррелированный поток, а не равномерный Poisson traffic.

Если каждый зритель получает HTML и два статических файла, CDN дополнительно обслуживает 300 млн requests; cached metadata добавляет ещё 100 млн GET на CDN. В локальной демонстрации эту роль выполняет Go-сервис. Для эфира static assets и неизменяемая публичная metadata выносятся в CDN. Получение cookie и персональный статус нельзя отдавать всем из shared cache. Origin получает `POST /api/session` даже при cached HTML; забыть выдачу cookie означало бы занизить оставшийся динамический поток вдвое.

Сетевой бюджет зависит прежде всего от заголовков, TLS и количества round trips, а не маленького JSON с номером варианта. При условных **2 KiB суммарных request+response на динамический round trip** 300 млн origin запросов дают 614,4 GB за эфир, или 10,24 GB/s = 81,92 Gbit/s в среднем на всю систему. С cached metadata 200 млн origin запросов дают 409,6 GB, 6,83 GB/s = 54,6 Gbit/s. Это wire-budget approximation без TLS handshake, TCP overhead, retransmits, статических файлов и CDN egress. При пике ×5 соответствующие бюджеты — около 409,6 и 273 Gbit/s. Размеры нужно измерять на реальном браузере и ingress.

Cookie в реализации выдаётся отдельным POST после загрузки вопроса. Если рендеринг выполняется на backend, нагрузка HTML тоже попадает на origin. Оптимизации frontend не должны менять семантику дедупликации.

## Подбор shard и API instance

Нельзя назначить число машин из рекламного benchmark PostgreSQL. Сначала измеряется устойчивый поток **новых** ballots на одном production-equivalent shard с нужными индексами, synchronous replica, размерами batches и допустимой p99 latency. Прогон, почти целиком состоящий из повторов, измеряет другой workload.

Обозначения:

```text
q = измеренный устойчивый поток новых ballots/с на shard
u = допустимая доля использования измеренной мощности, например 0,60
k = коэффициент кратковременного пика, например 5
S = ceil(k × Ravg / (u × q))
```

Примеры **условные**, `q` в них не измерен:

| Допущение о q | Shard для среднего при u=0,60 | Shard для пика ×5 при u=0,60 |
| --- | ---: | ---: |
| 25 000 ballots/с | 112 | 556 |
| 50 000 ballots/с | 56 | 278 |
| 100 000 ballots/с | 28 | 139 |

Значение `q` должно включать limit по latency, а не момент перед падением throughput. Необходимы отдельные резервы по ресурсам и отказам; эти примеры не являются гарантией пережить потерю дата-центра. Digest распределяет записи по shard независимо от популярности варианта, но проверять статистику реального распределения всё равно нужно.

В production требуется ограничить fanout ingress API к владельцам writer shard. Если каждый API process заводит pool ко всем `S` базам, число соединений растёт как `API_instances × S × pool_size`, а microbatches дробятся между процессами. Например, 200 API processes и pool=8 дают 1600 соединений **к каждой** базе. Локально прямые pools удобны; при сотнях shard нужны закреплённые writer groups, согласованная маршрутизация и/или иной проверенный механизм ограничения соединений. Такой router и управление владельцами — дополнительная **не реализованная** production-инфраструктура, необходимая перед заявлением national-scale capacity.

API sizing делается аналогично, но по origin requests/s, TLS termination и стоимости body validation/HMAC. Дешёвое вычисление HMAC не отменяет стоимость goroutines, память очередей, открытые sockets и response writes. Измерять только SQL benchmark недостаточно.

## Очередь, batch и сроки

При пропускной способности базы `q` и очереди `B` ожидающих работ задержка только от backlog примерно `B/q`. Если ingress выше egress, очередь заполняется со скоростью `Rin - q`. Она поглощает краткий джиттер, но не компенсирует недостающую мощность на минуту.

Пример: shard получает 50 тыс./с, а пишет 40 тыс./с. Очередь на 20 тыс. jobs заполнится примерно за 2с; её максимальный queue wait около 0,5с без новых проблем. Наращивать её до миллионов означает больше latency, memory и потерянных неподтверждённых запросов при restart. При заполнении нужны быстрый отказ, небольшой `Retry-After` и ограниченные повторы с jitter. Миллионы клиентов с фиксированным одинаковым retry interval создают повторную волну.

При batch=256 и 50 тыс. новых ballots/с на shard теоретический минимум около 196 batch commits/с. Это не обещание доступной мощности: часть batches неполная, внутри есть index work, выборы, locks, WAL и replication. Несколько writer workers улучшают parallelism, но добавляют contention и могут ухудшить p99.

Admission, flush, DB timeout и HTTP deadline должны образовывать единый latency budget. В реализации HTTP confirmation wait ограничен пятью секундами после enqueue, DB timeout на batch настраивается отдельно, по умолчанию две секунды. Ключевой контракт: «запрос попал в память» не равен «голос сохранён». При deadline/обрыве после возможного commit клиент повторяет тот же идентификатор. Новые голоса после конца окна не допускаются; финализация результатов ждёт всех допустимых незавершённых записей.

## Объём хранения и WAL

Уникальность требует помнить до 100 млн digest на опрос, а не только несколько counters. Реализованный логический состав — 32-byte HMAC, 16-byte poll ID, 8-byte mask и 8-byte received timestamp: 64 bytes без PostgreSQL overhead. Физическая строка имеет tuple overhead/alignment, уникальный B-tree имеет свои страницы и overhead. Благодаря mask множественный выбор не увеличивает размер самой строки.

Первый storage budget, **оценка для планирования**:

| Статья | Допущение | На 100 млн ballots |
| --- | --- | ---: |
| Heap + unique index + резерв страниц | 250–500 bytes/ballot | 25–50 GB на primary суммарно по shard |
| Primary + две полные replicas | ×3 | 75–150 GB |
| Backup одной полной копии | ещё ×1 без compression | ещё 25–50 GB |
| WAL за эфир | 300–1000 bytes/ballot, требует измерения | 30–100 GB |

Дополнительные индексы, autovacuum, bloat, full-page images, длительная WAL-retention и несколько одновременно хранимых опросов могут значительно увеличить budget. Эти оценки не дают лицензию выделить ровно 50 GB дисков: нужны свободное место для checkpoints, восстановления и архивов.

При таком условном WAL budget средний первичный поток составляет 0,5–1,67 GB/s на всю систему, при пике ×5 — 2,5–8,33 GB/s. Две replicas удваивают суммарный outbound WAL primary до 1–3,33 GB/s в среднем; это дополнение к пользовательскому трафику. Синхронная межплощадочная запись добавляет RTT и зависит от дисковой flush latency реплики. Репликационный поток, restore time и стоимость являются самостоятельными ограничениями.

Число counter rows порядка `S × L × (O+1)` на опрос (`L` lanes, `O` вариантов и дополнительный total), значительно меньше ballots. В реализации `L = WORKERS_PER_SHARD`, по умолчанию 4. Для 278 shard, 4 lanes и 10 вариантов — максимум 12 232 строки; условная production-конфигурация с 64 lanes дала бы 195 712. Но частота их UPDATE, dead tuples и locks важнее этого объёма; сверка с ballots не должна запускать массовый scan каждую секунду во время эфира.

## Обязательная программа испытаний перед эфиром

1. Получить workload: timestamp распределение зрителей, число статических и динамических запросов, retries и распределение выбранных вариантов.
2. Устойчивый тест одного shard: новые идентификаторы, правильные indexes, synchronous durability и replica; фиксировать offered rate, accepted unique rate, duplicate rate, p50/p95/p99, error rate, queue wait, CPU, disk latency, WAL/s и replica lag.
3. Полный путь браузера: first visit + cookie + vote, отдельно warm и cold caches; нагрузочный генератор не должен быть скрытым bottleneck.
4. Прогон 100 млн уникальных ballots за 60с на распределённой инфраструктуре с пиком, одновременно читающей результаты админкой и с настроенными ingress limits. Генераторы должны быть распределены по независимым узлам/сетям.
5. Повторы одного cookie, повтор после неизвестного commit, simultaneous choices, выключение API, отказ primary/реплики и потеря площадки. Проверять не только throughput, но и отсутствие двойного счёта и потерянных **подтверждённых** голосов.
6. После завершения проверить уникальность, совпадение счётчиков с ballots и полноту всех shard; опубликовать hardware, версии, конфигурацию, raw отчёт и методику.

Если нельзя выполнить пункт 4, допустимый результат — работающий сервис, обоснованный capacity plan и честные локальные измерения. Фраза «поддерживает 100 млн в минуту» в таком случае должна обозначать проектный target, а не доказанную характеристику.

Включённый `cmd/load` — closed-loop генератор: каждый из ограниченного числа worker завершает GET metadata, POST session и POST vote перед следующим участником. Он проверяет уникальные голоса, повтор с другим вариантом и итоговые option counts. Общий `elapsed_seconds` включает first-visit requests и проверки повторов, а `vote_latency_ms` измеряет только отправку первого vote, включая его retries. `accepted_per_second` считает ответы `201`; успешно сохранённые голоса, подтверждённые как `200` после неизвестного исхода, учитываются в `already_voted` и итоговой сверке, но не в этой rate-метрике. Ни эта rate-метрика, ни p99 closed-loop теста не показывают offered-rate latency при заданном телевизионном всплеске.

## Отказы и эксплуатационные ограничения

В базовой схеме один shard имеет один writable primary. Отказ primary делает его часть ключей недоступной до восстановления/проверенного failover; нельзя отправить эти ключи на пустую альтернативную базу и сохранить дедупликацию. За 60с даже несколько секунд failover значимы. Read-only replica не увеличивает write throughput.

Для RPO=0 подтверждённых голосов при потере primary требуется синхронная durable копия вне того же failure domain и fencing прежнего writer. Для потери целой площадки копия должна находиться в другой площадке; это одновременно требование к размещению и network latency. Automatic promotion, quorum/consensus менеджер и DNS/LB convergence в локальную реализацию не включены. RTO не задан числом без измеренного failover drill.

Масштабировать карту shard во время эфира нельзя: modulo при другом `S` меняет место записи digest. Даже изменение порядка тех же URL меняет маршруты. Нужны versioned map, сохранённая конфигурация опроса и миграция с проверкой целостности вне окна голосования. Все API nodes используют одинаковые cookie/dedup secrets; ротация dedup HMAC key до окончания retries может позволить повторный ballot. В текущем API повтор после закрытия получает `409`, поэтому проверка сохранённого ballot после неизвестного commit требует отдельной будущей receipt-функции.

Площадка, которая обслуживает 60% traffic, после потери соседней площадки не обязательно способна обслуживать 100%. Необходимо capacity reservation по выбранному сценарию отказа, а не только число replicas. В этой реализации нет утверждения о переживании одновременного отказа площадки и пика ×5.
